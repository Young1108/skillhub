# 需求调研材料汇总

一段录音 + 几个在线文档链接 → 一份能直接进需求评审的调研总结。

**这个 skill 的价值不在「总结」，在「取证纪律」**：异构材料里必然有假信息（转录错字、空壳文档、幻觉段），把它们当成事实写进结论，比不写更糟。

## 0. 先做材料清单，再动手

任何抓取动作之前，先列这张表。它是后面所有结论的可信度基础。

| 源 | 形式 | 取法 | 状态 |
|---|---|---|---|
| 面聊录音 | m4a 40min | 本地 Whisper 转录 | 待取 |
| 微信面聊总结 | doc.weixin.qq.com smartpage | CDP 渲染 | 待取 |
| 飞书 wiki ×N | 在线文档 | lark-cli docs +fetch | 待取 |

**逐个源确认它到底有没有内容**。这一步省不掉——本机踩过的最典型的坑是：四篇文档里三篇只有标题没有正文，如果不去判定，会误以为「需求评审已开过」，然后拿录音推断去补评审结论。

## 1. 录音：本地转录

直接用 `local-audio-transcribe` skill（MLX Whisper，40 分钟音频约 72 秒）。要点：

- `initial_prompt` 必须写本次领域术语（知识库/RAG/检索/询价/运价/渠道…），专有名词识别率提升明显
- 转录结果**必然有错字**，尤其是人名、系统名、工具名——同一人可能被写成三四种
- **噪声段会被"强行解码"成周期性重复的假文本**（同一句重复几十遍）。识别特征：连续 10 段以上文本几乎相同。这类段落一律剔除，不要试图理解

## 2. 飞书文档：拉取 + 空壳检测

```bash
python3 scripts/fetch_lark_docs.py ./out \
  https://<domain>.feishu.cn/wiki/XXXX \
  https://<domain>.feishu.cn/wiki/YYYY
```

脚本会输出一张表，标出每个文档是 `OK` / `EMPTY` / `FAIL`，并给出正文字数。

**空壳判定逻辑**：去掉 `<title>` 后正文不足 20 字 → `EMPTY`。这类文档 `revision_id` 通常是个位数（2），说明建完就没动过。

权限坑：企业 wiki 用默认 profile 常报 `3380004 No permission`。脚本支持用环境变量指定 profile（不硬编码，避免把内部租户名写进仓库）：

```bash
LARK_PROFILE=<你的企业 profile 名> python3 scripts/fetch_lark_docs.py ./out <url>…
```

优先试 `LARK_PROFILE` 指定的 profile，失败再退回默认 profile。`lark-cli profile list` 可查可用 profile。

## 3. 微信 / 企微文档：SPA 渲染抓取

`doc.weixin.qq.com/smartpage/...` 这类页面**不要用 curl**，返回的是 120KB 的空壳 HTML（只有「企业微信文档」五个字），正文全靠 JS 渲染。

**关键结论：带分享码（`scode=`）的页面不需要登录态也能看。** 用干净 profile 起独立 Chrome 就能渲染出来，不必复制本机 cookie。

```bash
bash scripts/grab_spa_text.sh "<url>" ./out/wechat.txt
```

脚本做的事：干净 profile 起 Chrome（`--no-sandbox` 必须加）→ Node 22 内置 WebSocket 直连 CDP → 轮询 `document.body.innerText.length` 直到连续 3 轮稳定 → 落盘 → 杀进程清 profile。

实测约 12 秒渲染出全文。若 `rc=3`（文本过短）说明撞上登录墙，此时才需要 `local-session-cdp-scrape` 的复用登录态流程。

## 4. 交叉核对：分层，不要混写

这是整个流程里最容易被跳过、后果最严重的一步。材料填进同一个文档后，读者无法分辨哪句是原话、哪句是推断。所以交付物里必须显式分四层：

| 层 | 含义 | 写法 |
|---|---|---|
| 录音确证 | 录音里明确说过 | 直接陈述 |
| 文档确证 | 文档正文写了 | 标注来源文档 |
| 推断 | 转录错字纠正、术语还原、常识补全 | 标「推断」并给原文 |
| 未辨识 | 完全听不出/看不出 | 列入附录，明确「不作为结论依据」 |

**人名、系统名、工具名一律进「未辨识」表**，除非有第二来源能对上。典型：同一人被转录成 4 种写法；wiki 标题和正文里同一人名的两个字不一致。

## 5. 输出骨架

固定这几节，顺序不要变：

```
一、调研概况          对象 / 参与人 / 范围 / 目的 / 材料来源表
二、结论速览          5–6 条，每条一句判断 + 一句依据
三、现状复述          按业务链路拆，标录音确证
四、需求清单          R1..Rn 表格：需求 / 优先级 / 验收要点
五、明确排除项        业务方当场否决的，防止后续反复
六、待确认问题        Q1..Qn 表格：问题 / 需确认人 / 影响
七、文档缺口          哪几篇是空的，进度实际到哪一步
八、下一步流转        谁在什么会上决定什么
附：未辨识内容       转录/识别不确定项对照表
```

需求清单的硬要求：

- 每条必须有**验收要点**，不能只写「优化XX」
- 优先级只用 P0/P1/P2，定义写清：P0 = 本期必做且无外部依赖
- 分期的判断依据是**依赖**，不是工作量。外部数据拿不到 → 二期
- 业务方说「不要」的功能进第五节，不进需求清单

## 6. 常见判断错误

| 症状 | 真相 |
|---|---|
| 把「准确率不高」当核心问题 | 往往是**责任归属**问题：用户不复用是因为 AI 不能替人担责，不是结果错 |
| 把业务方口述的规则直接当系统规则 | 业务口述的是「怎么灵活处理」，系统要的是「怎么稳定判定」，两者常常相反 |
| 忽略「业务方自己配置阈值」 | 边界类参数不要产品拍，要留成可配置项 + 默认安全值 |
| 把空壳文档算作已完成阶段 | 空壳 = 该阶段没发生。交付物里必须写「实际只到 X 阶段」 |
| 用常识填补转录缺口 | 远场录音必然有信息缺口，填空后当原话是硬伤 |

## 7. 收尾

- 录音原文、抓取的文档、检索脚本副本全部留在工作区同一目录，便于复核
- 临时 Chrome profile 必须清（`scripts/grab_spa_text.sh` 已用 trap 自动处理）
- 交付时先讲**材料完整度**（哪几篇是空的），再讲结论。顺序反了会误导决策
