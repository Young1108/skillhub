# 公司技术方案写作

## 入口限制

仅在满足以下任一条件时使用本 skill：

- 用户明确要求产出或处理“公司格式”“公司规范”“公司模板”的技术方案，或含义同等明确的公司制式技术方案。
- 用户要求按公司格式整理技术评审稿、评审会材料，或把技术方案压缩成评审文档。
- 用户显式调用 `$writing-company-technical-proposals`。

仅提到“技术方案”“方案设计”“架构设计”“设计文档”“实施计划”，或只是要求分析、实现、重构、评审代码，均不满足自动触发条件。未满足入口条件时，不加载本 skill 的模板与写作规则，按普通任务处理。

## 核心目标

按公司完整性要求产出可执行、可评审、可交接的技术方案。以证据支撑设计判断，用自然、平实的中文讲清背景、约束、取舍、实现和影响面。以“临时移交给其他开发仍能无缝推进”为完成标准，而不是机械填满章节或把方案写成宣传稿。

本文件负责任务识别、事实约束、工作流和最终验收。章节结构与中文写作细节按“参考资料路由”加载，避免把无关内容全部放入上下文。

## 任务类型

先判断用户需要哪一种结果：

| 类型 | 交付结果 |
|---|---|
| 新建方案 | 基于事实材料形成完整技术方案 |
| 补全方案 | 保留已有结论，补齐缺失设计与交接信息 |
| 表达改写 | 不改变已确认的技术含义，改善证据链、论证顺序和中文表达 |
| 完整性审查 | 先列问题、影响与优先级，再给可直接写回的内容 |
| 评审前检查 | 给出评审阻塞项、待确认项和附件缺口 |
| 技术评审稿 | 面向多角色的决策界面：速览、评审重点、术语、已定结论与残余风险 |

## 技术评审稿的硬要求

评审稿不是技术方案的缩写版。写作时同时满足：

1. 读者分层：项目经理看排期与依赖，产品看范围与口径，测试看状态与异常，接口对接方看契约；开发看实施方案。
2. 开头两节固定：**速览**（6 行以内：范围／不做／关键决策／依赖／主要风险／下一步）与**评审重点**（议题、请谁定、建议结论、不定会怎样）。
3. 一个术语表：覆盖项目内最易混的词对（例如「地址类型」「偏远类型」「地图」），全文只用一套叫法。
4. 决策可追溯：待定项编号、写 Owner 与后果；定稿后原地回填结论与日期，不删行。
5. 证据分层：结论 + 一行证据；文件行号、函数名、完整报文移入实施方案或附录。
6. 多个数据面先分表：说明各自来源、判定对象、失败语义，再写流程。

骨架、读者映射、决策闭环与协作排版细节见 [技术评审稿写法](references/technical-review-playbook.md)。

## 工作流

### 1. 建立事实清单

读取当前仓库和用户提供的需求、代码、接口、DDL、配置、部署、测试及项目管理材料。优先确认：

- 业务目标、范围边界与明确不做的事项
- 当前实现、目标实现和受影响模块
- 上下游系统、调用链路、数据流与责任边界
- 接口、表结构、中间件、定时任务和环境差异
- 性能、安全、兼容性、可用性与合规约束
- 开发、联调、测试、发布、回滚和运维责任

将信息区分为“已确认事实”“基于事实的推断”“合理假设”“待确认项”。事实必须能追溯到用户确认、需求、代码、配置、测试、DDL、接口契约、日志、指标、issue 或已有决策记录。材料之间冲突时指出冲突及其影响，不静默选择更方便的版本。

每个会影响技术选型、实施范围、发布或回滚的强判断，都要能回指证据。不得虚构文档链接、负责人、排期、资源、性能指标、接口字段或线上现状；无法验证的内容明确标为假设或待确认。

### 2. 决定章节范围（涉及结构或完整性时）

仅改中文表达且用户没有要求调整结构时，跳过本节。其他任务以参考模板的十一章为骨架，逐项判断标有“如需”的章节：

- 有实质设计或风险时保留并写清结论。
- 与项目无关时省略；若评审者可能误以为遗漏，保留标题并用一句话说明不适用原因。
- 信息尚未确认但会影响实施时保留，标为“待确认”，同时写明确认人或确认动作；不知道确认人时只写确认动作。

不要生成空标题、通用套话或与当前项目无关的最佳实践清单。

### 3. 编写可执行方案（需要新写或改写正文时）

仅清点章节、附件或阻塞项且不产出正文时，跳过本节。需要写正文时，先明确每一节在回答哪个评审问题，再组织材料。常用论证路径是：

`背景与约束 -> 已观察到的事实 -> 推断与取舍 -> 方案结论 -> 实现影响 -> 验证方式`

路径用于帮助读者理解判断来源，不要求每节机械套用同一组小标题。

每个关键设计点按以下结构表达：

1. **结论**：选什么方案，覆盖什么范围。
2. **依据**：业务约束、现状证据和取舍理由。
3. **实现**：模块职责、调用链路、数据变化、异常分支和关键配置。
4. **影响**：上下游、兼容性、数据、资源、发布与运维影响。
5. **验证**：如何测试、观测、验收和回滚。

结论可以前置，但后文必须给出对应依据。避免用“显然”“已经很清楚”“真正”“很顺”等作者感受代替证据、约束或影响。

#### 根因与目标机制

方案以已验证根因为设计起点，将目标行为落实到拥有该规则的模块。目标机制取代产生问题的旧逻辑，并清理旧逻辑衍生的旁路、重复校验和补偿分支。

阶段性止损措施作为独立方案项，写明适用范围、退出条件、验证信号和清理任务。根因仍在验证时，方案先定义诊断动作和临时措施；证据闭合后再确定长期机制。

接口设计至少包含调用方、提供方、协议、路径或方法、鉴权、请求响应、枚举、错误码、幂等与兼容策略。数据库设计至少包含字段语义、主键、索引、约束、容量预估、变更方式和回滚影响。涉及缓存、消息、任务或数据迁移时，写清一致性、重试、去重、补偿、生命周期和失败处置。

架构图、时序图、数据流图仅在关系用文字难以清楚表达时使用。优先采用可随文档维护的 Mermaid；若引用外部图，附可访问链接和必要文字说明。

### 4. 处理已有文档

补全时保留已经确认且有证据支持的结论，不为统一文风而改变技术含义。

改写前先做结构诊断：

1. 标出会影响设计或实施的强判断。
2. 检查判断是否有事实依据，推断是否写明前提。
3. 检查前文提出的问题或风险，后文是否给出回答。
4. 先重排缺失或错位的论证，再处理句子和措辞。

需要提出改写建议时，优先提供可直接写回的内容，不只给“表达不清”“论证不足”一类抽象评价。

审查时按以下顺序输出：

1. 评审或实施阻塞项
2. 高风险缺失项
3. 一般完整性问题
4. 可直接写回原文的修改内容
5. 待补附件与待确认清单

问题必须指向具体章节或结论，说明缺失造成的实施、测试、上线或交接影响。

### 5. 完整性检查

交付前逐项检查：

- 背景、目标、范围和需求依据是否明确
- 核心流程、模块职责和上下游边界是否可追踪
- 接口、数据、异常和非功能设计是否足以实施
- 风险、依赖、兜底与回滚是否可操作
- 测试范围、环境、造数与验收口径是否明确
- 发布步骤、监控告警和故障应急是否可执行
- 排期、人力、资源和任务看板是否有真实依据
- 关联文档与模板附件是否齐全或明确列为待补
- 新接手开发是否能定位代码、配置、数据和责任人
- 评审者能否直接定位关键结论、依据、影响和待确认项
- 评审稿是否具备速览与评审重点，且每条待定项都有 Owner 与「不定会怎样」
- 评审稿是否残留实现细节（文件行号、函数名、完整报文），是否与实施方案形成第二事实源
- 多数据面结论是否分别写明来源、判定对象与失败语义，而不是合并成一条
- 强判断是否能回指事实，推断、假设和待确认项是否明确区分
- 长期方案是否基于已验证根因，由目标机制取代旧逻辑；阶段性措施是否具备退出条件和清理任务

交付包含正文新写、改写或表达审查时，再检查：

- 同一模块、指标、状态和动作是否始终使用同一套术语
- 是否存在删掉后不影响事实或论证的过场句、空评价或宣传式黑话

若信息不足，仍可先输出有价值的方案骨架，但必须在开头列出会阻塞结论的关键问题，并在文末集中列出待确认项。不要用猜测填补空白。

## 输出约定

- 默认输出 Markdown，沿用模板的中文章节编号。
- 面向内部评审者和实施者，语气平稳、具体，重点解释条件、对象、关系、结果和取舍。
- 结论优先，正文使用具体系统名、模块名、接口名和表名；术语确定后全文保持一致。
- 长方案需要 TL;DR 时，优先概括问题来源、关键约束、方案决策和主要影响，不复述目录。
- 技术评审稿先给「速览」与「评审重点」，再进正文；已定项写「定稿 + 依据 + 日期」，未定项写「请谁定 + 不定会怎样」，不用「建议」代替决定。
- 内容天然是目标、风险、影响面或实施项清单时直接使用列表，不强行改成长段。
- 链接尽量指向具体文档或看板；没有真实链接时写“待补充：资料名称”，不生成示例网址。
- 最后附“待确认项”和“配套附件”清单；两者为空时可以省略。
- 用户指定更短的决策记录或特定调用方文档时，按其范围裁剪模板，不扩写无关平台内容。

## 示例

用户：“根据这个需求和当前代码，按公司格式写一份支付回调改造技术方案。”

执行：读取需求与回调实现，确认调用方、幂等键、状态机、重试、签名校验、数据变更、灰度与回滚；再按模板保留相关章节。无法确认的峰值并发和第三方重试规则列入待确认项，不自行填写数字。

用户：“把这份方案压成评审稿，会上要过。”

执行：先写速览与评审重点（议题、请谁定、建议结论、不定会怎样），再写术语与状态表；文件行号与完整报文留在实施方案，评审稿只留结论与一行证据。评审后把「建议」改成「定稿 + 日期」。

不触发示例：“分析支付回调的现状并给出改造方案。”该请求没有明确要求公司格式、公司规范或公司模板，应按普通技术分析任务处理。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 所有可选章节都保留并写“暂无” | 按项目风险决定保留或省略 |
| 用合理猜测补齐链接、排期或指标 | 明确标为待确认并给确认动作 |
| 只描述目标，不写调用链与异常分支 | 写到其他开发可直接实施和测试 |
| 审查只给问题清单 | 同时提供可直接写回的修改内容 |
| 只写上线步骤，不写观测与回滚条件 | 补齐验证信号、触发条件和操作步骤 |
| 用“打通、闭环、落地、很顺”代替具体设计 | 写明谁调用谁、数据怎样变化、约束和结果是什么 |
| 同一对象反复更换近义词 | 先确定模块名、指标名、状态词和动作词，再全文复用 |
| 一开始就逐句润色 | 先检查证据和论证顺序，再处理中文表达 |
| 评审稿写成方案缩写版，塞入文件行号与实现细节 | 只留结论与一行证据，细节回指实施方案 |
| 待定项只写「建议方案 A/B」 | 写清请谁定、建议结论、不定会怎样，定稿后回填日期 |
| 把多个数据源合成一条结论 | 先列数据面（来源、判定对象、失败语义）再写流程 |

## 示例附件

本公开版本**不附带真实项目文档**：公司内部方案与评审稿含系统名、接口路径与同事姓名，不适合公开。

需要示例时，用自己手头的材料对照以下要点：

- **技术方案**：看术语是否先定义后使用、模块与依赖是否成表、接口与数据颗粒度是否够他人直接实现、非功能与风险是否写到触发条件。
- **架构稿**：看模块所有权表、版本与一致性、调用链与架构风险是否有对应小节。
- **评审稿**：对照 `references/technical-review-playbook.md` 的十三节骨架，重点看速览、评审重点（请谁定 / 建议结论 / 不定会怎样）、术语表、状态表与决策收口。

不要把内部文档直接放进公开仓库；如需本地留存，放在 `~/.agents/skills/writing-company-technical-proposals/agents/examples/` 这类不发布的目录。
