# 中文技术方案论证与表达指南

本指南用于新写或改写中文内部技术方案正文。目标是让评审者看清判断从哪里来，让实施者知道要改什么、影响什么、怎样验证。它不改变公司模板，也不要求所有方案形成同一种文风。

## 一、先整理判断与证据

先找出文中会改变设计、范围、排期、发布或回滚方式的判断，再检查证据。按以下类型标记材料：

- **事实**：用户已确认的需求，或能从代码、配置、测试、DDL、接口契约、日志、指标、issue、决策记录中直接确认的内容。
- **推断**：由一个或多个事实归纳出的判断，需要写清推断前提。
- **假设**：为了继续设计而暂时采用、尚未验证的条件。
- **待确认**：缺少后会阻塞设计、实施或验收的事项。

常用论证顺序：

`事实 -> 约束或规律 -> 方案取舍 -> 实现影响 -> 验证信号`

不要从一个实现细节直接跳到架构结论。材料不足时缩小结论强度，或把缺口列入待确认项。

### 示例

较弱：

> 当前回调链路已经很清楚，适合统一收口。

较强：

> 支付平台的三类回调目前分别更新订单、退款单和通知记录，但都需要重复执行验签、幂等检查和事件落库。方案将这三个步骤集中到 `PaymentCallbackService`，业务状态更新仍由各处理器负责。

后一种写法给出了观察对象、重复行为、设计边界和保留的职责。

## 二、按读者问题组织正文

每一节应能回答一个评审或实施问题，例如：

- 为什么现在需要改？
- 当前实现和约束是什么？
- 选择了什么方案，排除了什么？
- 模块、接口和数据分别怎样变化？
- 哪些上下游会受影响？
- 失败时怎样发现、处置和回滚？

长方案可在开头增加简短 TL;DR，优先覆盖：

1. 问题来源和目标。
2. 影响决策的关键约束。
3. 方案结论、主要影响和仍待确认的风险。

不要在 TL;DR 中复述目录，也不要解释“下文将如何展开”。

## 三、改写时先改结构，再改句子

收到已有草稿时：

1. 标出最强的设计判断和承诺。
2. 检查每个判断是否有证据，是否把推断写成了事实。
3. 检查背景提出的问题、风险或目标在后文是否得到回答。
4. 把证据、取舍、结论和影响放回合适位置。
5. 最后处理冗余句、术语和中文表达。

保留有证据支持的技术含义。若原文无法支持结论，指出缺口并降低结论强度，不擅自补造事实。

## 四、让句子承载信息

技术方案中的句子优先交代以下内容：

- 条件：在什么场景或约束下。
- 对象：哪个模块、接口、表、角色或指标。
- 关系或动作：谁调用谁，谁写入什么，状态怎样变化。
- 结果：带来什么影响，怎样观测或验证。

如果一句话只是在主持文章，例如“接下来进入真正的问题”“这张图想说明的事情很简单”，通常直接删除。下一句应直接提出问题或解释关系。

少用作者感受代替技术判断：

| 空表达 | 改写方向 |
|---|---|
| `这套方案很顺` | 指明顺在职责边界、调用次数、延迟还是发布步骤 |
| `这个问题会变得很现实` | 写出触发条件、具体风险和受影响对象 |
| `链路已经很清楚` | 列出调用方、处理步骤、数据变化和异常分支 |
| `这个方向很值得推进` | 写出收益、成本、风险和验证依据 |

避免用对立句式制造没有证据的强调。确有方案对比时，直接列出比较维度、约束和取舍。

### 直接描述目标行为

使用肯定句说明责任主体、触发条件、执行动作和预期结果。将双重否定、绕行表达和依赖错误状态的描述，改写为目标状态或允许条件。

| 绕行表达 | 直接表达 |
|---|---|
| `接口不再不校验签名` | `接口在处理业务数据前校验签名` |
| `未命中规则时不创建通知` | `系统仅在规则命中时创建通知` |
| `不是由 Worker 直接写表，而是由 Service 处理` | `Worker 发布事件，Service 负责持久化` |
| `不允许无管理员权限的用户访问` | `接口仅向具备管理员权限的用户开放` |
| `不继续保留旧处理分支` | `迁移完成后删除旧处理分支` |

安全边界优先写成允许条件。排除项本身属于业务事实时，直接说明排除对象、适用条件和系统行为。

## 五、把黑话还原成设计事实

遇到抽象词时，不做机械同义替换；先判断句子真正要表达的动作、对象或约束。

| 常见词 | 优先写清的内容 |
|---|---|
| `赋能` | 哪个角色新增了什么能力 |
| `闭环` | 从哪个动作开始，经过哪些状态，如何确认完成 |
| `打通链路` | 哪个系统以什么协议调用哪个接口，传递什么数据 |
| `统一收口` | 哪些入口改为经过哪个模块，原入口如何处理 |
| `沉淀` | 内容保存到哪个文档、表、配置或流程 |
| `落地` | 在哪个模块实现，何时发布，如何验收 |
| `底座` | 具体提供哪些公共接口、数据或运行能力 |
| `一站式` | 用户能在同一入口完成哪些明确操作 |

这些词不是禁词。只有在具体关系已经写清时才保留。

## 六、保持术语和语义系统一致

首次出现时确定正式名称，后文保持一致：

- 模块名、接口名、表名和字段名与代码或契约一致。
- 指标名与计算口径一致。
- 状态词与状态机一致，不用位置隐喻代替状态变化。
- 同一动作使用同一动词，例如“筛选、聚合、命中、升级”不要随段落任意换成近义词。
- 中英文混用以项目已有术语为准，不为显得专业临时引入英文词。

## 七、选择合适的表达形态

以下内容天然适合列表：目标、范围、约束、方案比较、风险、影响面、实施项、待确认项和验收条件。

只有当关系或时序难以用短段落说明时才画图：

- 架构图表达组件及依赖。
- 时序图表达跨系统调用和异常分支。
- 数据流图表达数据来源、处理和去向。
- 状态图表达允许的状态变化和守卫条件。

图后直接解释关键关系和设计结论，不用“这张图很清楚”一类过场句。

## 八、控制读者负载

评估方案可读性时看两个维度：

1. **答案跳转层数**：读者从问题出发，需要跨多少章节、图表或外部链接才能找到结论和依据。
2. **脑内状态**：读者需要同时记住多少未声明前提、术语别名、远处例外和状态变化。

### 减少答案跳转

- 将关键结论、直接依据和主要影响放在同一节或相邻位置，不让读者自行拼接散落信息。
- 正文保留理解决策所需的最小上下文。外部链接用于提供权威证据和完整细节，不能代替核心答案。
- 易变化的字段清单、配置值和接口细节以权威来源为准；正文概括它们对方案的影响，避免复制出第二份事实源。
- 相邻章节如果只是在不同标题下重复同一批事实，应合并或重写。每一层结构都应完成一种信息转换，例如事实汇总、约束归纳、方案决策、影响分析或验证定义。

### 减少脑内状态

- 约束和不变量放在首次影响设计的位置，不要求读者记到远处才看到例外。
- 状态、角色、接口和数据来源集中表达；关系复杂时使用表格、状态图或数据流图。
- 异常规则靠近对应流程，避免把正常流程和失败处置拆到无法互相定位的章节。
- 同一对象只使用一个正式名称。必须引入别名时，在首次出现处明确映射。

### 读者测试

交付前用以下问题做诊断：

- 新评审者能否在一分钟内找到为什么要改、决定了什么、影响谁、主要风险和待确认项？
- 对任意关键数据或状态，能否快速回答它从哪里产生、由谁修改、在哪里持久化、如何观测？
- 对任意关键结论，能否在附近找到事实依据、约束和方案取舍，而不需要连续跳转多份材料？

一分钟是发现导航问题的诊断尺度，不是对整篇方案的硬性阅读时限。复杂内容可以长，但关键答案应容易定位。

## 九、中文表达检查

交付前检查：

- 强判断是否有事实依据，推断和假设是否明确。
- 章节是否在回答具体问题，前文提出的风险后文是否处理。
- 是否只讲抽象概念，没有落到模块、接口、数据和影响面。
- 是否存在删掉后不损失信息的主持句或过场句。
- 是否用“很顺、显然、真正、很清楚”等感受词代替约束或结果。
- 是否用黑话掩盖了调用关系、数据变化或责任边界。
- 模块名、指标名、状态词和动作词是否前后一致。
- 句子是否直接描述目标行为、适用条件和责任主体，双重否定是否已转换为肯定表达。
- 本来适合列表或图的内容是否被写成难以扫描的长段。
- 修改表达时是否意外改变了已确认的技术含义。

发现问题时优先给出可直接写回的句子或段落，而不是只做抽象点评。
