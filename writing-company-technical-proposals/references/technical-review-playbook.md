# 技术评审稿写法（多角色评审会）

本文件解决一个独立问题：**评审会现场要用的评审稿怎么组织**。它不是技术方案的缩写版，读者也不是实施者。

技术方案回答「怎么实现，交接给谁」；技术评审稿回答「要不要做、做到什么程度、谁来定、风险多大」。同一项目通常两份都要有，评审稿是压缩后的决策界面。

## 一、何时用

- 需要组织或参加技术评审会，材料要在 30 到 60 分钟内被产品、测试、项目经理和接口对接方读完。
- 已有完整方案，需要压出一份评审稿。
- 评审后要把结论回填，形成可追溯的决策记录。

## 二、读者映射

| 角色 | 主要看 | 需要带走什么 |
|---|---|---|
| 项目经理 | 速览、排期、依赖、风险 | 谁在什么时候交付什么；哪些事阻塞开工 |
| 产品 | 范围、口径、异常话术、验收 | 对客会看到什么；哪些边界不做 |
| 测试 | 状态表、异常分支、埋点、验收映射 | 分支是否穷举；证据怎么取 |
| 接口对接方 | 接口契约、鉴权、错误码、字段 | 交付什么接口；字段与失败语义 |
| 开发 | 改动面与契约 | 通常看实施方案，不看评审稿 |

评审稿只写前四类读者需要的内容。文件行号、函数实现、完整报文移入实施方案或附录。

## 三、骨架（十三节）

| 节 | 作用 | 判据 |
|---|---|---|
| 修改记录 | 谁在何时改了什么 | 每次定稿追加一行，不覆盖 |
| 速览 | 一页决策界面 | 6 行以内：范围／不做／关键决策／依赖／主要风险／下一步 |
| 评审重点 | 会议议程 | 每条写「请谁定」与「不定会怎样」 |
| 术语与缩略词 | 消除歧义 | 必须覆盖项目内最易混的词对 |
| 背景与目标 | 为什么做 | 一句话 + 约束表（标注来源） |
| 功能现状 | 现在有什么 | 能力／现状／对本期影响，只写结论与一行证据 |
| 已有接口 | 用哪些、不用哪些 | 服务／接口／用途／本期处理 |
| 功能架构 | 谁和谁有关系 | 一张分层图 + 模块职责表 |
| 流程与状态 | 正常与异常怎么走 | 主流程图 + 状态表 + 失败语义 |
| 接口契约 | 对接方要看的部分 | 请求／响应示例 + 字段表 + 错误码；可放附录 |
| 埋点 | 数据方与测试 | 事件 + 字段 + 落库前置 |
| 已定口径与风险 | 决策与残余风险 | 已定项写结论与依据；待确认项写 Owner 与时间点 |
| 测试关注点 | 测试照着建用例 | 按类别列，不追求覆盖全部 AC |

超过 60 行的单节通常意味着把实施方案内容搬进了评审稿。

## 四、决策闭环

评审稿的价值在于把「待定」变成「已定」并可追溯：

1. 每个待定项编号（G1、G2…），写清现状、影响、建议、Owner。
2. 必须写「不定会怎样」，否则无法判断优先级。
3. 定稿后**原地回填结论与日期**，保留编号和删除线，不删行。
4. 已定项不再写「建议」，改写「定稿」。
5. 全部定稿后，把「待确认」表压成「剩余外部确认」（只留真正的第三方事项）。

反例：用「建议方案 B」代替决定，会期结束后没人知道到底选了哪个。

## 五、证据与边界

- 评审稿只放结论和一行证据；证据链放实施方案或附录。
- 事实分级用固定符号（代码实证／文档明确／推断／待确认），全文一致。
- 数字必须来自实查，并注明口径与日期（例：生产库 8,657 条画像中 3,064 条含 FedEx 证据，2026-11-09）。
- 区分「代码设计如此」与「现网实际如此」。开关、环境差异必须写明：本地分支落后远端 145 个提交、`SMARTY_ENABLED=false` 都会让纸面结论失真。
- 引用代码时给分支（`origin/main`）而不是「仓库里」，避免读到旧检出。

## 六、多个数据面要分开写

一条业务结论由多个数据源拼成时，先画一张「谁产出什么、互不推导」的对照，再写流程。

示例（地址类型判断）：

| 数据面 | 来源 | 判定对象 | 失败语义 |
|---|---|---|---|
| 地址类型 | FedEx 地址校验 | 门牌级地址 | 失败即无类型结论 |
| 偏远类型 | 后台偏远邮编库 | ZIP5 | 失败不等于未命中，需补说明 |
| 地图 | Google Static Maps | 坐标 | 失败保留文字，单独提示 |

没有这张表，评审者会把三个来源当成一件事，后续讨论口径时反复回到原点。

## 七、常见退化

| 退化 | 表现 | 修正 |
|---|---|---|
| 写成长篇实现说明 | 列文件、函数、行号、类名 | 移到实施方案；评审稿只留「改哪里、影响什么」 |
| 复制接口全文 | 与实施方案出现两份契约 | 评审稿留字段表与示例，细节回指 |
| 待定项只写「建议」 | 没有 Owner 与时间点 | 补「请谁定」「不定会怎样」 |
| 用「已确认」包装推断 | 没有实查或截图 | 降级为推断，或先查再写 |
| 只有正常流程 | 没有失败、降级、重试 | 加状态表与失败语义 |
| 术语一名多义 | 同一概念三种叫法 | 建术语表，首次出现处确定正式名称 |

## 八、评审稿自检（一分钟）

- 一分钟内能否回答：为什么做、决定了什么、谁定、风险多大、下一步是什么。
- 每个「已定」是否有结论、依据、日期。
- 每个「待确认」是否有 Owner 和「不定会怎样」。
- 评审稿里是否还残留文件行号、函数名、完整报文。
- 术语表是否覆盖了项目里最容易混的两个词。
- 图是否超过三张，是否每张都在回答一个问题。

## 九、协作与排版（飞书文档）

多人同时编辑时，这些操作会踩坑：

- **写前重新 fetch，写后核对**：revision 会在别人编辑时跳变，长 pattern 容易匹配失败。
- **表格内 `str_replace` 的 pattern 不要带竖线**：跨单元格会返回 `1011 no document changes`；给表格加行用整表 replace。
- **删表行会留空行断表**：批量改表后跑一次「孤儿行」检查（表格行之间不得出现空行）。
- **版本号不要全局替换**：两个需求同号过一次（2.2.2／2.2.3），改完全局搜一遍。
- **mermaid 图**：用 ```mermaid 直接写，插入后数 whiteboard 块数与预期一致，再导出预览核对。
- **图不超过三张**：架构、主流程、时序；其余用表。
- **追加行不要用整篇 append**：会复制整份文档，删除重复块要用块级删除。

## 十、评审后动作

1. 结论回填评审稿与实施方案，注明日期。
2. 新建或更新配套子文档：自测集、踩坑记录、评测集说明（按项目需要）。
3. 未决事项转成任务，写清 Owner、阻塞对象和验证方式。
4. 把本轮新踩的坑写进踩坑记录，格式统一为：现象 → 根因 → 处置 → 防护。

## 十一、示例附件

`agents/examples/` 下有三份真实文档：

- 对应的真实评审稿：评审稿快照（两需求合并评审），含速览、评审重点、术语表、状态表与决策收口，Mermaid 源码可直接改。
- 对应的真实项目文档：公司格式技术方案，覆盖一～七章；对照术语挂法、模块依赖、数据库与接口颗粒度、非功能与风险。
- 对应的真实项目文档：架构设计（评审稿），覆盖一～八章；对照模块所有权表、版本与一致性、调用链与架构风险，图片已本地化。

阅读方式：先按第三节骨架对照目录，再按第四节检查「已定／待确认」的写法；示例中的数字与姓名属内部信息，对外使用前需脱敏。
